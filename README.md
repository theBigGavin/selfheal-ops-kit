# Self-Heal Ops Kit

> 给跑定时 agent / cron 任务的人：任务坏了没人知道、修了又误报、降载忘了恢复——这三件事一次配好。
>
> 状态：**开源内测免费，托管版筹备中**。

Self-Heal Ops Kit 是一套直接从生产环境沉淀下来的「定时任务自愈」模式与脚本：它不要求每个脚本自己上报故障，而是直接扫描调度引擎自带的失败信号（`last_status` / `failure_streak` / `last_error`），失败即自动建运维工单，连续失败自动升级，误报有新鲜度闸门，过载降载可逆自动恢复。

## 解决什么问题

用 cron / agent 定时任务干活的人（独立开发者、一人公司、小团队 SRE）都遇到过：

| 痛点 | 本 Kit 的模式 |
|---|---|
| 任务静默失败，几小时甚至几天后才有人发现 | **失败信号直接读调度引擎状态**（jobs.json 的 `last_status=error`），不依赖脚本自觉上报——上报逻辑本身就是最容易坏的环节 |
| 失败了但没有工单，全靠人肉记忆 | **失败即建卡**：幂等键 `fail-<job>-<error_hash>`，同 job 同错误只开一张卡，修好复发自动开新卡 |
| 告警刷屏：错误早就修了，旧状态反复触发新告警 | **新鲜度闸门**（`FRESH_HOURS`）：超过时间窗的历史残留 error 直接跳过；连续失败链因 `last_run_at` 持续刷新不受影响 |
| 反复失败没人升级，一次性失败又过度反应 | **分级升级**：`failure_streak≥N` 自动升 P0 + 最高优先级 + 事件留痕 |
| 过热/内存紧张时停了服务，忘了恢复 | **可逆降载**：降载动作登记到 `selfheal_state.json`，条件滞回（温度/内存双阈值）自动恢复 |
| 巡检脚本自己坏了怎么办 | **静默契约 + catch-all**：无动作零输出（零 token），自身异常永远 exit 0，不 cascade |

## 快速上手

1. 复制 `scripts/cron-selfheal-monitor.py` 到你的机器。
2. 按脚本 docstring 里的 env 变量表配置（`OPC_HOME`、`OPC_CRON_DIRS`、`OPC_KANBAN_DB` 等；无 kanban 系统时可用 dry-run 先看动作）。
3. 先跑一次演练模式：
   ```bash
   OPC_SELFHEAL_DRY_RUN=1 OPC_SELFHEAL_DEBUG=1 python3 scripts/cron-selfheal-monitor.py
   ```
   stderr 会列出将要建的卡/评论/升级，不落库。
4. 确认无误后挂进你的调度器（建议 30min 一次），按你团队的派活方式接建工单命令即可。

## 设计要点（为什么这样做）

- **读引擎状态，不信脚本自觉**：调度引擎的失败计数是最不会说谎的信号源。脚本自觉上报的链路（脚本→总线→路由→建卡）每一环都可能断。
- **建工单走官方 CLI，不直写数据库**：任务状态机（tasks + events + runs）是内核所有权，脚本直写=复制语义，引擎升级即漂移。只读探测例外。
- **幂等键 + done 后缀**：内核幂等会命中已完成的卡，因此复发场景键加 `-r<completed_at>` 确定性后缀开新卡，既不重复开卡也不漏复发。
- **一切外化到文件/CLI**：巡检脚本自身零依赖单文件，失败面最小。

完整决策对比（为什么 CLI 建工单而不是直写 DB、为什么 30min 而不是 5min、G 卡知情路径等）见 `docs/design.md`。
